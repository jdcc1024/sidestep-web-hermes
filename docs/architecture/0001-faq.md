## Decision

**The answer source is one typed TypeScript file, `content/faq.ts`.** Each entry
is `{ id, question, answer, finePrint?, published }`, with `answer` a string in a
tiny Markdown subset (paragraphs, `**sub-heading**` lines, `-` bullets, `1.`
lists, `[text](href)` links). Prices are interpolated from `lib/pricing.ts` with
template literals, so the compiler (not a token system) keeps the FAQ and the
calculator in step. Order is array order.

One pure module, `lib/faq.ts`, parses an answer once into a small block AST and
has two renderers: React (the site) and plain text (the clipboard). No new
Convex function, no new dependency, no new service.

**Copy buttons are admin-only (JCC, D9 = B)**, decided client-side from the
Convex `users.isAdmin` cache via the existing `users.getCurrentUser` query. See
"Admin check for the copy buttons" below.

**Content/code boundary (JCC, D10):** every FAQ string (entries *and* the
section heading, subtitle and "Didn't see your question?" CTA) lives in
`content/faq.ts`. Adding, rewording, reordering, hiding or publishing an entry
edits only that file. No JSX, no component, no test other than the content lint
changes. `FaqSection` holds no literal copy.

```
  JCC edits                 lib/pricing.ts ──(template literal)──┐
      │                                                          ▼
      ▼                                     ┌────────────────────────────┐
  content/faq.ts  ─── FaqEntry[] ─────────► │ lib/faq.ts (pure, tested)  │
  (local edit or                            │  publishedFaqs()  gate     │
   Claude Code)                             │  parseAnswer()  → Block[]  │
                                            │  toPlainText()  → string   │
                                            │  faqUrl / faqCopyText      │
                                            └──────┬──────────────┬──────┘
                                  server render    │              │  plain text (string)
                                                   ▼              ▼
                      FaqSection (RSC) ── items ──► FaqAccordion ("use client")
                      renders Block[] + finePrint   hash ↔ open item, scroll, focus
                                                    CopyAnswerButtons (per open item)
                                                      │  useIsAdmin() ── false ─► null
                                                      ▼ true
                                             navigator.clipboard.writeText
```

Analogy: `content/faq.ts` is a config file with a schema (the `FaqEntry` type)
and a lint pass (`content/faq.test.ts`). `lib/faq.ts` is the compiler with two
back ends.

## Options considered

| | (a) Typed TS file ✅ | (b) Markdown files + frontmatter | (c) Convex table + admin editor |
|---|---|---|---|
| Edit path | local edit / Claude Code → commit → deploy | same | `/admin` form, live instantly |
| Prices from `lib/pricing.ts` | template literal, typechecked | needs a `{{token}}` system | needs a token system + runtime lookup |
| New code | ~1 lib module + 1 data file | + frontmatter parser (or `gray-matter`), fs reads, token substitution | schema, public query, 3 admin mutations with auth, editor UI, seed, sanitising |
| Marketing page | stays static RSC | stays static | becomes Convex-dependent (loading state, a public query to secure) |
| History / rollback | git | git | none unless built |
| Build issues | 2 + content | 3 + content | 3–4 for the source alone |

**Why not (b).** Nicer to edit for long prose, but these answers are 1–6 short
paragraphs. It costs a parser or a dependency, loses type-checking, and the Q1
price rule forces a home-grown token language. All cost, no gain at 8 entries.

**Why not (c).** It is the only option that removes the deploy from the edit
loop, and that is the one thing (a) can't do. But UX estimates JCC edits these a
few times a year. (c) also adds a public read path and admin write path to
secure, turns a static page into a live-data one, and on its own uses up the
3-issue pilot budget before a customer sees anything.

**Upgrade triggers (a) → (c):** JCC edits more than about monthly, or wants to
edit from his phone without waiting for a deploy, or wants private answers or
per-customer snippets that must not be on the public site. The `FaqEntry` shape
and `lib/faq.ts` carry over unchanged: only the loader changes. So (a) is not a
dead end.

Also rejected: a Google Doc/Sheet as the source (new integration plus runtime
fetch and caching, for a list of 8 items), and `react-markdown` (a dependency
that still leaves the plain-text renderer to write; the subset is ~100 lines).

## Data shape

```ts
// lib/faq.ts
export type FaqEntry = {
  /** Permanent deep-link slug: /#faq-<id>. Never rename or reuse once published. */
  id: string;            // /^[a-z0-9]+(-[a-z0-9]+)*$/
  question: string;
  /** Markdown subset, see below. */
  answer: string;
  /** Plain text, rendered small and muted under the answer. Never copied (D5). */
  finePrint?: string;
  /** false = draft: never rendered, never copied. */
  published: boolean;
};

type Inline = { kind: "text"; text: string } | { kind: "link"; text: string; href: string };
type Block =
  | { kind: "heading"; text: string }            // a whole line `**text**`
  | { kind: "p"; content: Inline[] }
  | { kind: "ul"; items: Inline[][] }
  | { kind: "ol"; items: Inline[][] };
```

Markdown subset, chosen to match what the approved §3 copy actually uses:
- A blank line separates blocks. Consecutive `- ` lines form a `ul`, and
  consecutive `<n>. ` lines form an `ol`. Inside a list, a line with no marker
  continues the previous item (leading spaces trimmed, joined with a space), so
  Q4's wrapped steps work. Other lines in a block join with a space into a `p`.
  Source line breaks therefore never matter: "verbatim" means the same words
  after whitespace is collapsed.
- **Sub-heading (D7):** a line that is exactly `**text**` (nothing else on the
  line) is a `heading` block, and the lines under it (until the next blank
  line) are a separate `p`. So `**Screen Glow vs Fabric**\nYour phone…` →
  `[heading, p]`. `**` anywhere else is literal text; we don't need inline
  bold, so we don't build it.
- `[text](href)` inline links. `href` must be a same-site path (`/…`, `#…`) or
  `https://…`. Anything else (for example `javascript:`, `http:`) renders as
  plain text. **`https://` = external**: rendered as `<a target="_blank"
  rel="noopener noreferrer">`; `/` and `#` render as `next/link`.
- Anything else is literal text. No HTML, no `dangerouslySetInnerHTML`, so an
  editing mistake can make a sentence look odd but can never break the page or
  inject markup.

Rendering: `heading` → `<h4>` styled bold in the foreground colour (the section
is `h2` and Base UI's `Accordion.Header` renders `h3`, so `h4` keeps the outline
correct). `finePrint`, when present, renders as its own `<p>` after the answer
blocks, smaller than the answer text, `text-muted-foreground` (an AA token), and
before the copy buttons. It is not parsed as Markdown.

### Plain text (`toPlainText`, the clipboard)

| Block / inline | Plain text |
|---|---|
| `p` | inlines joined; blocks separated by one blank line (`\n\n`) |
| `heading` | its text with no `**`, then **one** `\n`, then the next block (it belongs to that block) |
| `ol` / `ul` items | `1. ` `2. `… / `• `, one per line |
| same-site link (`/`, `#`) | its text only |
| external link (`https://`) | its text in place, **and** its URL on its own line directly after the block that contains it (D7) |

`finePrint` is not part of `answer`, so it is excluded by construction.
`faqCopyText` then appends `\n\n` + the deep link, which is always the last line.

Content example:
```ts
// content/faq.ts
import { DESIGN_FEE } from "@/lib/pricing";
import { formatTierPriceList, priceRange } from "@/lib/faq";
const FROM_10 = { fromQuantity: 10 } as const; // A4 = A: don't list 5–9
export const FAQ: FaqEntry[] = [
  { id: "cost", question: "How much do custom jerseys cost?", published: true,
    answer: `Jerseys are ${priceRange(FROM_10)} each, and the more you order, the less each one
costs: ${formatTierPriceList(FROM_10)}. Tax and shipping are included, so there are no hidden fees.

Want us to design it for you? That's a flat $${DESIGN_FEE} design fee, tax included. …` },
  …
];
```

`formatTierPriceList()` / `priceRange()` are derived from `PRICING_TIERS` (same
pattern as `formatTierRange` in `lib/pricing.ts`), so changing a tier price
changes the FAQ with no edit to `content/faq.ts`. Both take an optional
`{ fromQuantity }` that drops tiers ending below it. **No price literal in
`content/faq.ts`:** `$125` appears in both `cost` and `design`, and both
interpolate `DESIGN_FEE`.

**The FAQ and the calculator deliberately disagree on the minimum (JCC, A3 +
D1b).** The FAQ says "Our minimum is 10 jerseys per design." and the `cost`
answer lists tiers from 10 up, to steer new customers to 10+ (runs under 10 are
expensive to source). The calculator keeps quoting 5–9 at $60 because repeat
customers need that number (`MIN_ORDER_QUANTITY` = 5). Neither `lib/pricing.ts`
nor the calculator changes in this initiative. The `minimum` answer is
hand-written (its "10" is policy wording, not interpolated), and no test
asserts that it matches `MIN_ORDER_QUANTITY`. A comment above the entry says so.

### The publish gate (defence in depth)

`publishedFaqs(entries)` returns entries where `published === true` **and** the
question, answer and fine print contain no `[CONFIRM`. The second check is at
runtime on purpose: an edit that skips `npm run verify` (a quick local edit, or
later the GitHub web editor) must still never ship a forgotten `[CONFIRM]`.
`FaqSection` is a server component and filters before anything reaches a client
component, so drafts are not in the RSC payload or the client bundle either.

`content/faq.test.ts` is the lint pass: ids unique and slug-shaped, every
published entry passes the gate, every answer parses into at least one block,
and **every id in a pinned `PERMANENT_IDS` list still exists and is published**.
Deleting or renaming a published id fails `verify`, and that is how "a copied
link keeps working" is enforced rather than just hoped for. Adding an id to the
list is the deliberate step when a new entry is first published.

## Deep links

- URL: `/#faq-<id>`, as UX specified. It is a fragment, so no routing change;
  Next serves `/` as today. `id="faq-<id>"` goes on each `AccordionItem`, with
  `scroll-mt-20` to clear the 64px sticky nav.
- `FaqAccordion` (client) controls the Base UI `Accordion` `value`. On mount and
  on `hashchange` it matches `^#faq-([a-z0-9-]+)$`. If the id is published it
  opens that item alone, scrolls it into view (`behavior: "smooth"`, or
  `"auto"` when `prefers-reduced-motion: reduce`) and focuses its trigger with
  `preventScroll`. For an unknown id or any other hash it does nothing and
  throws nothing. Plain `#faq` (the nav link) just scrolls to the section.
- **`<Reveal>` comes off the FAQ section** (`app/page.tsx`). A deep link lands
  mid-page, so the scroll-triggered fade and 24px rise would play on exactly the
  content the visitor asked for, and the rise would shift it under the nav just
  after we positioned it. The FAQ is a destination, not scenery.
  `scripts/check-reduced-motion.mjs` samples `#faq` as its revealed section, so
  it moves to `#quote` (the next section, also below the fold). Rejected: a
  "skip if hash matches" prop on `<Reveal>`. It is more code in a shared
  component to save one section's fade.

## Copy action

| Button | Clipboard |
|---|---|
| Copy answer | `toPlainText(parseAnswer(answer))` + `"\n\n"` + `faqUrl(origin, id)` (fine print excluded) |
| Copy link | `faqUrl(origin, id)` = `` `${origin}/#faq-${id}` `` |

- `origin` = `process.env.NEXT_PUBLIC_SITE_URL` if set, else
  `window.location.origin` at click time (like `CopyInviteLinkButton`). There is
  no production site yet (A1), so without the override a link copied on
  `localhost:8080` would be useless to a customer. Set it to the Tailscale
  Funnel URL (or later the real domain) and links are right wherever JCC copies
  from. Unset, it behaves as before. It's a public, non-secret value.
- The server computes the plain text and passes it to the client as a string
  prop. The client never parses Markdown.
- UI follows the `CopyInviteLinkButton` pattern: outline `Button`, check icon
  and "Copied!" for 2 s, sonner success toast, and on clipboard failure an error
  toast that contains the text. The buttons render inside the Accordion panel,
  so collapsed items (unmounted panels) show neither.

### Admin check for the copy buttons (D9 = B)

**Decision: a client hook, `useIsAdmin()` in `lib/useIsAdmin.ts`, that reads
`isAdmin` from the existing public `users.getCurrentUser` Convex query, gated
on `useConvexAuth().isAuthenticated`.** It returns `true` only when the query
has returned a user row with `isAdmin === true`; loading, signed out, no row
and `false` all return `false`. `CopyAnswerButtons` returns `null` (no wrapper,
no spacer) unless it's `true`, and owns its own top margin, so a non-admin
panel ends exactly where the answer (or fine print) ends.

```
Clerk private metadata {"isAdmin": true}      (server-only, Clerk dashboard)
      │  refreshFromClerk action → Backend API fetch → isAdminFromClerk()
      ▼
internal.users.applyClerkUser  ──► users.isAdmin (Convex cache)   ← only writer
      │
      ▼  public query, args: {}, returns the CALLER's own row only
api.users.getCurrentUser ──► useIsAdmin() ──► CopyAnswerButtons: null | buttons
```

Options considered:

| | (1) `getCurrentUser` cache ✅ | (2) Next route / server action calling Clerk | (3) Server-render the check in `FaqSection` | (4) Clerk session claim / public metadata |
|---|---|---|---|---|
| Page stays static | yes | yes | **no** (dynamic per request) | yes |
| New server surface | none | new endpoint to secure | none | Clerk config |
| Clerk API calls | none per view (cache) | one per signed-in page view | one per request | none |
| Freshness | refreshed once per browser session by `UserSync` | live | live | at token refresh |
| Invariants | kept | kept | kept | **broken**: admin path via public metadata/claims |

Why (1): it adds zero server code, reuses a query every signed-in page already
subscribes to via `UserSync` (Convex dedupes identical subscriptions, so it's
not even an extra round trip), and keeps the marketing page static: during SSR
and before auth resolves the hook returns `false`, so the HTML has no buttons
and hydration matches; admin buttons appear once the query answers (the
accepted "flash of no buttons"). Why not (2): a new endpoint plus a Clerk
Backend API call per page view, to decide whether to show two buttons that
copy public text. Why not (3): D9 says the page stays static. Why not (4): it
creates exactly the admin-from-public-metadata path the invariants forbid.

Security invariants (`sidestep-website-dev`), checked:
- **No public Convex function accepts `isAdmin`.** This design adds no Convex
  function at all. `getCurrentUser` takes `args: {}` and derives the user from
  `ctx.auth`, so a caller can only ever read their own row.
- **No public-metadata / `is_admin` path.** The client never reads Clerk
  metadata or session claims. The only source is the Convex cache, whose only
  writer is `internal.users.applyClerkUser`, fed by `isAdminFromClerk()` on a
  server-side Backend API fetch of *private* metadata.
- **Hiding is convenience, not security.** `useIsAdmin` must carry a comment
  saying it is a UI hint and must never authorise anything (server code keeps
  using `requireAdmin` / the admin layout's Clerk check). A user who patches
  the JS to show the buttons gets a copy of text that is already on the page.
- **Staleness is harmless.** A revoked admin can see the buttons until
  `UserSync`'s next refresh (next browser session). They expose nothing.
- **No new data exposure.** `getCurrentUser` already returns the caller's own
  row (name, email, `isAdmin`) to their browser today via `UserSync`.

## Security review

- **New server functions: none.** No Convex function, no API route. The data is
  public marketing copy, published on purpose. The one read the client makes
  (`getCurrentUser`) already exists and is self-scoped.
- Drafts are filtered on the server, so an unpublished entry is not in the HTML,
  the RSC payload or the JS bundle. Note: it is still in git. If the repo is
  public, drafts are readable there, which is acceptable for FAQ drafts.
- Content can't inject markup: rendering goes through React elements, and link
  `href`s are allow-listed. External links get `rel="noopener noreferrer"` so
  the opened page can't reach `window.opener`.
- Clipboard writes happen only in click handlers. Nothing is read from the
  clipboard.

## Launch-state rule (so each step keeps the site coherent)

**F-01 is a pure refactor for the visitor.** It migrates the **4 live answers
verbatim** (questions and answers byte-identical to today's `FaqSection.tsx`)
as `published: true` (minimum, timeline, design, shipping), so the only visible
change is the approved subtitle, CTA and nav link. It adds the approved §3 text
for `cost`, `process` and `colour` as `published: false`, and the Q6
`design-tips` draft verbatim (with its `[CONFIRM]`) as `published: false`.
Putting `colour` in at F-01 means the content lint proves the new sub-heading
and external-link syntax against the real answer, not just fixtures.

**F-02** adds deep links and the admin copy buttons; content is unchanged.

**F-03 is the content pass, and the proof of D10:** a diff to `content/faq.ts`
alone replaces the questions and answers of `minimum` (D1b), `timeline` and
`design` (plus its `finePrint`, D5) with §3's approved text, replaces the
`design-tips` draft with the approved Q6 (D6b), publishes `cost`, `process`,
`design-tips` and `colour`, and extends `PERMANENT_IDS` to all 8 ids. ss-dev
does it (P1 = B:
nothing is pushed before Gate 2, so the GitHub web editor can't be the dry
run). JCC's own "one place I edit" check happens at Gate 2: edit
`content/faq.ts` locally and reload.

Why not fold F-03 into F-01 now that all wording is approved: F-01 would then
be both a refactor and a copy change, its regression check ("site unchanged")
would disappear, and we'd lose the one-file diff that demonstrates the content
boundary works. The cost of keeping them apart is one small content card.
